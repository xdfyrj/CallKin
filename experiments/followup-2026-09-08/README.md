# CallKin 후속 연구: 관계 합의 조건의 효과

2026-09-08. 제출용 PDF와 분리한 새 실험이다. 모든 대상은 이미 결과를 본 개발 프로그램이며, 새로운 원본에서의 검증이 아니다.

## 확인한 답

fd와 zoxide에서는 관계 합의 조건이 정밀도를 올렸지만 F1과 원본별 평균 재현율은 낮췄다. ripgrep에서는 본문 전용 후보가 예산을 넘었고 관계 합의 구성은 완료했다. 이 경우 계산 가능성 효과는 확인했지만 두 방법의 품질 우위는 직접 비교하지 못했다.

단순한 정규화 토큰 정확 일치도 프로그램마다 달랐다. zoxide에서는 강한 기준선이었지만 ripgrep에서는 대형 오병합을 만들었다. 모든 프로그램에서 우세한 구성은 없었다.

## 비교 조건

- plain O3S의 전체 대상과 사전 함수 경계, 본문과 그래프를 고정했다.
- body2는 Token과 CFG의 교집합이다. combined3는 여기에 Relation의 선택도 요구한다. 임의 두 경로 합의와 body2는 다르다.
- combined3(k)는 body2(k)의 부분집합이다. 관계 조건으로 정답 후보 수가 늘 수는 없다.
- k16이 주 비교, k8과32는 민감도 분석이다. 기존 Align/Decide/complete-link는 수정하지 않았다.
- 구성마다 비교10,000회, 정렬500,000,000칸을 적용했다. 추가 교차 비교도 센다. 큐가 예산을 넘으면 미완료이며 품질0점으로 처리하지 않는다.
- 검색 설정18개 중13개 완료,5개 예산 거부다. 기준선6개와 Rescue3개를 포함해27개 구성 중22개 예측을 완료했다.

규약과 표본은 ba1a214, 실행 전 보충은0ccf51a, 최초 실행기는06c905a에 고정했다. 재현 불일치 처리 보충은 fd의 새 품질 결과를 보기 전8d5375c에 기록했다. 최초 시도는 로컬 archive/에 보존했다.

## 주 비교 결과

아래는 기존 정답 기준이다. 수정 정답은 별도 민감도로 다룬다.

| 구성 | ripgrep F1 | fd F1 | zoxide F1 |
|---|---:|---:|---:|
| 관계만 V0 | 0.0098 | 0.3849 | 0.1983 |
| 정규화 토큰 정확 일치 | 0.0036 | 0.2362 | 0.5703 |
| 본문2중 합의 + 판정 | 예산 거부 | 0.0555 | 0.0297 |
| 관계 포함3중 합의 + 판정 | 0.1817 | 0.0524 | 0.0282 |
| 3중 합의 + 판정 + Rescue | 0.2991 | 0.0524 | 0.0282 |

fd에서는 body2의 TP93/FP81이 combined3에서 TP87/FP56이 됐다. 정밀도는0.5345에서0.6084로 올랐지만 정답6쌍을 잃었다. zoxide는 TP19/FP19에서 TP18/FP15로 바뀌었다.

실제 정렬 칸은 fd에서400,208,901에서69,293,751로, zoxide에서103,728,338에서33,679,941로 줄었다. ripgrep body2는 사전 요구량15,552회/1,263,244,132칸으로 거부됐고 combined3는 실제3,192회/296,377,911칸을 소비했다. 요구량과 실제 소비량을 구분한다.

전체 정수와 원본별 지표는 [결과표](results-tables.md), [CSV](results-summary.csv)에 있다. zoxide 정확 일치는 쌍 F1이 가장 높지만 원본별 평균 재현율은 V0보다 약간 낮다. 한 지표만으로 우위를 주장하지 않는다.

## 손실의 원인

[단계별 기록](stage-details.json)은 정답 쌍의 관측, 비교 미도달, 구조, 슬롯, 병합과 복구를 나누어 합계를 검산한다.

zoxide body2-k16의 정답1,242쌍은 관측 자격 밖186, 비교 미도달460, 구조 탈락241, 슬롯 탈락336, 복구19로 나뉜다. 슬롯 탈락 중294개는 데이터 참조 채널만 달랐고, 정보 채널이 전혀 없는 경우는3개였다. fd에서도 슬롯 탈락702개 중496개가 데이터 참조 채널만 달랐다.

데이터 참조의 완전 일치 조건이 큰 손실 원인이지만, 조건을 없애면 된다는 결론은 아니다. 정확 일치는 zoxide에서 TP562/FP167을 만들었으나 ripgrep에서는 FP431,270개를 만들었다. ripgrep의 한 집단에는 정답 라벨296종류의 함수888개가 들어갔다.

정확 일치의 실제 정의는 실행 전에 선택한 TokenProfile.exact_token_hash다. 명령어, 피연산자 모양, 상수 범주와 제어 흐름 종류를 포함한다. 원시 바이트나 정확한 상수 값, 구체 데이터 주소, 소스 이름의 동일성이 아니다. [별도 검산](independent-baseline-check.md)은 zoxide의 수치를 기존 채점기로 확인했고 이름표 누출을 발견하지 않았다. 더 좁은 명령어/피연산자 키는 FP만3개 늘렸다. 이는 추가 민감도 관찰이며 주 기준선은 바꾸지 않았다.

zoxide body2의 TP는 k8에서18, k16/32에서19였고 fd combined3는 모든 k에서87이었다. 후보 증가가 일관된 복구 향상을 주지 않았다. Rescue는 ripgrep의 기존 ReadByLine 집단에서만325쌍을 추가했다.

## 정답 감사와 수정 민감도

프로그램마다 무작위10건과 목적6건을 골랐다. 총48건은 프로그램별 원본 그룹이며 서로 다른 소스 정의48개를 뜻하지 않는다. 무작위30건과 목적18건을 합쳐 전체 오류율로 해석하지 않는다.

[감사 요약](audit-summary.csv): 소스와 일치하는 것으로 검토한45건, 충돌2건, 미확정1건이다. LLM 에이전트의 소스 검토와 추가 정적 대조이며 외부 사람의 독립 감사나 컴파일러 내부 원본ID 검증은 아니다. source-consistent는 기록된 근거와 모순을 찾지 못했다는 뜻이다.

| 프로그램 | 기존 그룹 | 구분한 소스 위치 |
|---|---|---|
| zoxide | parse_line 아래 closure3개 | autojump.rs42,45,48행 |
| fd | build_overrides 아래 closure2개 | walk.rs339,344행 |

서로 다른 closure가 같은 정규화 경로로 합쳐져 있었다. [정적 확인 코드](verify_closure_sites.py)는 보존 ELF의 함수 범위, 원시 심볼과 소스별 오류 메시지 참조를 대조한다. zoxide45행은 직접 호출하는 작은 포맷팅 함수 안의 메시지로 확인했다. DWARF 원본ID 증명으로 표현하지 않는다.

원래 정답은 보존하고 [별도 수정본](audit-corrections/)에서5개 함수를 소스 위치별로 나눴다. 양성 분모는 zoxide에서3쌍, fd에서1쌍 줄고 음성이 그만큼 늘었다. 이번 방법들은 해당 쌍을 묶지 않았으므로 TP/FP는 같고 FN만 줄었다. [민감도 결과](audit-sensitivity.json)에서 주 비교 방향은 유지됐다.

ripgrep의 공유 주소는 서로 다른 메서드를 가리켰지만 기존 정답이 이미 자리표시자와 중립 규칙으로 표현했다. 이를 정답 오류로 세지 않았다. zoxide의 추가 Cow 심볼 관련1건은 미확정으로 남겼다.

기존 Cargo 소스 해시는 ripgrep의 crates/ 작업 공간 소스를 포함하지 않는다. 현재 Git 버전과 파일 해시는 기록했지만 과거 빌드 당시의 작업 공간 전체를 확정하지는 못했다.

감사 전문: [zoxide](audit-zoxide.md), [fd](audit-fd.md), [ripgrep](audit-ripgrep-main.md).

## 재현 과정에서 확인한 차이

zoxide의 k16 후보는 보존 후보와 일치했지만 fd와 ripgrep의 일부 후보/순위는 달랐다. 입력 provenance와 검색 코드/프로파일은 같았다. fd 확인 쌍은 현재 합산에서0.5833333333333334, 순차 합산에서0.5833333333333333이었고 후자가 보존 값과 같았다. [Python 공식 문서](https://docs.python.org/3.12/library/functions.html#sum)도3.12에서 부동소수점 합산 변경을 명시한다. 원래 F5의 정확한 실행 환경을 이 관찰만으로 확정하지는 않는다.

이후 비교도 모두 동일한 Python3.12.3을 사용했다. 점수 반올림과 임계값 변경은 하지 않았고, 과거 후보 완전 재현에 성공했다고 처리하지 않았다. 차이는 cache의 reference-drift.json에 남겼고 [검산 요약](reproduction-checks.json)에 함께 정리했다. 세 프로그램의 combined3-k16 strict 분할은 보존된 분할과 일치했다. zoxide의 최초/후속5개 주 예측 파일 해시도 같았다.

최대2개 사례를 병행했으므로 시간은 단일 관측이지 격리된 성능 벤치마크가 아니다. 공통3-view 후보 생성 비용은 별도 기록했으며 body2만의 전체 검색 시간을 독립 측정한 것은 아니다. 가상 주소 공간12GiB와 실행당30분 보호를 적용하고 실제 최대RSS를 기록했다.

## 직접 확인하는 방법

[검산 ZIP](verification-bundle.zip)을 풀고 실행한다.

```sh
python3 recheck.py
```

표준 라이브러리와 묶은 기존 linkage 규칙으로 실제 예측 집단에서22개 결과의 TP/FP/FN/TN을 재계산한다. 예산 거부5개는 NA로 남기며 수정 정답의 민감도도 확인한다. 원래 작업 경로와 분리된 임시 폴더에서 통과했다. 새 예측 생성이나 외부 사람의 검증을 뜻하지 않는다.

작은 관측자료에서 예측부터 확인하려면 다음을 실행한다.

```sh
python3.12 experiments/followup-2026-09-08/minimal/replay.py
```

[최소 예제](minimal/README.md)는 약196KB이며 이름 없는20개 함수에서 F5/F6를 실행하고 두 예측 저장 뒤 정답을 읽는다. body2는172회/9,159칸, combined3는113회/7,242칸을 사용했고 둘 다 TP26/FP0/FN0이었다. Rust 재빌드와 발견/본문 추출은 포함하지 않는 관측자료 재생이다.

큰 관측자료의 위치와 해시는 inputs.json에 있다. 해당 경로가 존재하는 환경에서는 다음을 실행한다.

```sh
python3.12 experiments/followup-2026-09-08/run_matrix.py
```

동일 신원의 완료 결과는 재사용하고 다른 신원이나 부분 결과는 덮어쓰지 않는다. 새 측정은 기존 실행을 보존한 별도 시도에서 해야 한다. 큰 관측자료의 완전한 배포와 소스부터의 자동 재생성은 남아 있다.

## 완료 범위와 다음 질문

완료: 규약/표본 고정,48건의 예비 소스 감사,27개 구성의 실행 기록, closure 수정 민감도, 원본별 지표와 단계별 손실, 작은 관측자료 재생,22개 보존 예측의 분리된 재채점.

미완료: 새로운 원본에서의 일반화, 소스부터 전체 재생성, 외부 사람의 독립 검증, 선택률을 맞춘 관계 음성 대조, 외부 유사도 방법 비교. 기존 정답 전체가 검증됐다고 주장하지 않는다.

다음 질문은 데이터 참조의 완전 일치가 언제 유효한 구별 근거이고 언제 같은 원본의 타입별 변형을 잘라내는가이다. 현재 결과만으로 조건을 없애자는 결론은 낼 수 없다. ripgrep의 정확 일치 오병합과 zoxide의 정답 손실을 함께 설명할 가설이 필요하다.

[교차검토](council.md)와 [코드 경로 지도](architecture/architecture.md)를 보존했다. Understand-Anything 실행 플러그인이 없어 관련13개 모듈의 수동 범위 지도만 작성했으며 전체 자동 분석으로 표시하지 않았다.
